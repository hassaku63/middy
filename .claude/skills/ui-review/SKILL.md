# ui-review

画面を、作った文脈を知らない目で見直すための手順（#286 のスライス 3）。指摘は原則からの**仮説**で、実測ではない。CI を落とす根拠にはしない（`docs/design/ux-principles.md` の「指摘の書き方」）。決定的に確かめることは、今どおり E2E と axe に書く。

## いつ使うか

- 画面の構成・配置・状態の見せ方（固定と追随、待ち、エラー）を変える PR を出す前。
- 配置の案（`?lab` で切り替える試験）を見比べるとき。案ごとに撮って、同じ手順で 2 回レビューさせる。
- 文言だけ、色のトークンだけの小さな変更には使わない。

## 手順

1. **画面を動かす。** E2E と同じく `make up` で起動する（`docs/dev/testing.md` の「通しの E2E」）。別の場所で動かしているなら `E2E_BASE_URL` でその URL を指し、手元の Chromium を使うなら `E2E_CHROMIUM_PATH` で実行ファイルを指す。
2. **撮る。** `cd frontend && npm run ui:shots`。
   - 状態ごと（最初の画面、例を開いた、和音を固定した、2 往復目）に、1280×800 と 390×844、ライトとダークで、`frontend/ui-review-out/` に `*.png`（全体）と `*.aria.yaml`（アクセシビリティツリー）を書く。
   - 対象は `E2E_BASE_URL`（既定は :8080）。試験の配置は `UI_SHOTS_LAYOUT=<クエリ>`（例: `UI_SHOTS_LAYOUT=lab`）で撮る。
   - 撮る状態を足すときは `frontend/e2e/ui-shots.spec.ts` の `states` に足す。
3. **契約を集める。** `docs/product/experience.md` の「画面の約束」から、対象の画面の節を写す（主目的、主操作、常に出す／必要なときだけ／出さない）。PR や試験の意図（何を確かめたいか）を 1〜3 行で添える。
4. **レビューさせる。** 文脈を共有しないサブエージェント（Agent ツール、`general-purpose`）を 1 つ起動する。渡すのは次のものだけにし、自分の見立ては渡さない。
   - 画像と `.aria.yaml` のパス（全部でなくてよい。見比べたい状態とサイズに絞る）
   - 3 の契約と意図
   - `docs/design/ux-principles.md` の 3 章（原則）と 6 章（確かめ方、認知的ウォークスルーの 4 つの問い、指摘の書き方）
   - `.claude/skills/hci/index.md`（判断の問いを引かせる）
   - 依頼文の例は下にある。
5. **確かめる。** 返ってきた指摘を 1 件ずつ見て、次の 3 つに分ける。
   - コードや画面で裏が取れたもの
   - 誤読（画像の読み違い、契約にない前提）
   - 判断が要るもの

   誤読は捨てる。裏が取れたものを、指摘の書き方の表で PR の「原則の点検」か、企画の Issue に書く。所有者の見立てがあれば、一致・不一致を添える。

### サブエージェントへの依頼文（例）

> あなたは middy の画面を初めて見るレビュアーです。添付の画面の画像と、アクセシビリティツリー（`.aria.yaml`）を見て、次の画面の約束と意図に照らしてレビューしてください。
> 主要なタスク（〈例: イメージを送って例を聞き、和音の成り立ちを読む〉）の 1 歩ごとに、認知的ウォークスルーの 4 つの問いを当ててください。原則は `docs/design/ux-principles.md` の 3 章、根拠は `.claude/skills/hci/index.md` の項目名で示してください。
> 指摘は「どこで／種類／重大度／確信度／改善案と確かめ方」の表で、重大度の高い順に最大 10 件返してください。画像から読み取れないこと（動き、音、時間の経過）は推定と明記してください。良い点も 3 件まで挙げてください。
> 〈画面の約束と意図をここに貼る〉
