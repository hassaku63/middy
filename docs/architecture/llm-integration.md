# LLM 連携の方針

## 役割分担（ADR-0003）

| 担当 | やること | やらないこと |
| --- | --- | --- |
| LLM | イメージ文の解釈、音楽パラメータ（`MusicalIntent`）の提案、ユーザーとの対話、解説文の言い換え | 音符の生成、コードの構成音の決定、分析結果の捏造 |
| `music` エンジン | 進行→タイムライン生成、分析、SMF | 自然言語の理解 |

理由: 音符レベルの生成を LLM に任せると、再現性・検証可能性・説明との一致が失われる。パラメータだけなら JSON Schema で縛れ、理論エンジンで検証できる。

## 境界

`backend/internal/llm`:

```go
type Client interface {
    Complete(ctx context.Context, req Request) (Response, error)
}
```

- `Request.OutputSchema` を指定すると構造化出力（JSON）を要求する。
- `fake.Client` は台本どおりに返す。台本がなく構造化出力を求められたときは、入力の気分語から決定論的な見本 Intent を返す（開発と E2E 用）。**ユースケースのテストはすべて fake で書き、CI はネットワークなしで通す。**
- 実アダプタは `internal/llm/anthropic`（BL-011）。プロバイダ固有の型はそこから外に出さない。

## Anthropic アダプタ（`internal/llm/anthropic`）

- SDK: `github.com/anthropics/anthropic-sdk-go/v2`（Go 1.25 以上を要求する。Go の版は `.tool-versions`）。生 HTTP は書かない。
- モデル: 既定 `claude-opus-5-5`（`ANTHROPIC_MODEL` で上書き）。意図解釈は短い出力なので、コストが問題になったら評価セット（BL-015）で `claude-sonnet-5-5` を比較してから切り替える。
- 構造化出力: `llm.Request.OutputSchema` を `output_config.format`（`json_schema`）として送る。`tool_choice` の強制は使わない。API は JSON Schema のサブセットだけを受け付け、それ以外のキーワードはリクエスト時に 400 になる（fake では検出できない）。`intent.Schema` は `TestSchemaUsesOnlySupportedKeywords` で守る。
- 思考: パラメータは省略（モデル既定の adaptive）。`output_config.effort` は `low`（`Config.Effort` で変更可）。
- 拒否・打ち切り: `stop_reason` が `refusal` なら `llm.ErrRefused`（アダプタが包んで返す）、`max_tokens` なら `ErrTruncated`（構造化出力の途中切れは使えないためエラー扱い）。
- 拒否への対応: 安全分類器は確率的に判定し、無害な音楽の相談でも誤検出がある（評価セットで `reasoning_extraction` を 1 件観測）。`ideas.Service` は拒否されたら同じ要求で 1 回だけ再試行し、2 回とも拒否なら `ErrDeclined` を返す。HTTP では 422 `llm_declined` になり、UI は言い回しを変えるよう促す。公式ドキュメントは、出力の項目でモデルの推論や思考過程を求めるとこの拒否が起きやすいとしているので、`reason` は「短い解説」として求める。サーバー側 fallback（別モデルへの切り替え）は SDK の beta API が必要なので導入していない。再試行しても拒否が残るようなら検討する。
- enum の大文字小文字: 構造化出力は enum の値の大文字小文字を保証しない。`music.Mode` は大文字小文字を区別せずに読み、`intent.Parse` はパターン id・スタイル・押し・格子の声部と `basedOn` を、前後の空白を除いて小文字にそろえる。ローマ数字は大文字小文字に意味があるので触らない。
- タイムアウト: 60 秒（`Config.Timeout`。考える時間を含め、`MaxTokens` まで書き切れる長さ。評価と同じ）。SDK の既定リトライ（2 回）は 429 / 5xx / 接続エラーに効く。
- プロンプトキャッシュ: システムプロンプトを 1 ブロックで送り、`cache_control: ephemeral` を付ける。可変部分（会話）は後ろ。
- エラー: `*anthropic.Error` はステータスとリクエスト ID を含めて包み直す。`ideas.Service` はすべて `ErrLLMUnavailable` として扱い、HTTP は 502 にする。
- テスト: `httptest.Server` が録画相当の Messages API 応答を返し、送信した本文（system のキャッシュ指定、messages の役割、`output_config`）を検証する。実 API を叩くテストは置かない（評価セット BL-015 が手動実行で担う）。
- 配線: `LLM_PROVIDER=anthropic` と `ANTHROPIC_API_KEY` を、起動時の環境変数で渡す（ADR-0011）。鍵がなければ起動時に設定エラー。実 LLM での起動は人が行い、エージェントは起動済みのサーバーに触る。

## プロンプト設計の原則

- システムプロンプトは `ideas.SystemPrompt()` がプロセス内で 1 度だけ組み立てる固定文字列。伴奏・ドラム・ノリの一覧は `pattern` のカタログから生成するので、カタログを変えればプロンプトと `intent.Schema` の enum が同時に追従する。

- システムプロンプトは「音楽理論の家庭教師」として役割と守ることを伝える。出力の形式は構造化出力が保証するので、プロンプトでは指示しない。
- 調のモードは major / minor / dorian / mixolydian（ADR-0015）/ phrygian（BL-189）。プロンプトは各モードの特徴と、ローマ数字をそのモードの音階に対して書くことを伝える。
- 拍子（`meter`）は 4/4 が既定で、3 拍子が典型のイメージ（ワルツ、ジャズ・ワルツ）では 3/4、付点 4 分の 2 拍で揺れるイメージ（ゆりかごの子守唄、舟歌、ジグ）では 6/8（ADR-0017）。プロンプトは型のカタログを拍子ごとに並べ、3/4 では和音の長さを 1 小節か 2 小節に、6/8 では半小節・1 小節・2 小節にし、テンポを付点 4 分の速さで書くこと（ADR-0019）を伝える。`Validate` は、拍子と和音の長さ、拍子と型の食い違い、6/8 のスウィングを落とす。
- ケルトの舞曲では、リールに `reel` と `bodhran`、ジグに 6/8 のドラム `jig` と伴奏 `rocking-6` か `arpeggio-6` を勧め、8 ビートとストロークを使わないよう伝える（BL-107）。主音を持続させたい静かな曲には `drone` を勧める（BL-108）。ジャズには 4/4 の `comp` と `jazz-ride` とスウィングを勧め、8 ビートとボサノバのドラムを使わないよう伝える（BL-081）。ジャズ・ワルツには 3/4 の `jazz-waltz` とスウィングを勧める（3/4 でもスウィングできる）。
- 候補は最初にスタイル（`style`）を選ぶ（BL-082）。プロンプトはスタイルの一覧を、それぞれに合う伴奏・ドラム・ノリと一緒にカタログから生成して並べる。`Validate` は、スタイルに合わない型とノリを、合うものを添えて落とす（ケルトに 8 ビートやストローク、ジャズに 8 ビートなど）。評価のケースは、最初の候補のスタイルを指定できる（#129）。
- 分数コードは、ラベルの `/` のあとにベースの調の度数を書く（`I/3`、`i/#7`。ADR-0020）。プロンプトは、度数が和音の何度かではなく調の度数であることを例（`V7/V/#4` は D7/F#）で示し、下がるベース、ライン・クリシェ、ペダルの書き方を短い断片で見せる（BL-115）。進行まるごとの例は、評価で 5 件の最初の候補にそのまま写されたので載せない。
- 和音の長さは `beatsPerChord` で一律にでき、和音ごとに変えるなら `beats` に書く（BL-109）。プロンプトは、ケルトや民謡では主和音を長く保つと素朴さが出ること、毎小節同じ間隔で替えるとポップスに聞こえやすいことを伝える。`Validate` は、長さの数、拍子が許す長さ、小節の切れ目（ADR-0017 の決定 2）を検査する。和音の長さとスタイルの整合は検査しない（プロンプトの指示だけ）。
- ドラムは型の id（`drums`）の代わりに格子（`drumGrid`。BL-077、ADR-0012 の決定 2）でも書ける。声部は `{voice, steps}` の配列で書く（`intent.GridSpec`。声部ごとの任意の欄を 12 個並べたスキーマでは、実 API の応答が返らなくなった）。プロンプトは任意の欄として 1 文だけ伝える: カタログでは足りない打ち方（ハーフタイム、キメ、型の 1〜2 打の変化）が欲しいときだけ書き、もとにした型を `basedOn` に書く。`Validate` はエンジンの検査（`pattern.GridDrums`）をそのまま再試行の理由にし、`drums` との併用を落とし、`basedOn` が拍子とスタイルに合うかを見る（スタイルの検査は `basedOn` で行う）。評価のレポートは `strum/grid<eight-beat` と書く。
- 調が変えてしまうラベルの再試行の文には、エンジンの直し方に加えて、大文字の和音が根音の上のセカンダリードミナントを指していそうなら、それも添える（C major の `II7` なら「`V7/V`」）。根音で書いた属七が裏コードを指していそうなら、それも添える（C major の `bII7` なら「`subV7/I`」、`bVI7` なら「`subV7/V`」。BL-129）。シャープの根音で書いた減七にも、経過の減七を添える（C major の `#i°7` なら「`vii°7/ii`」。BL-131）。短調では、向かう先を大文字の `V` で書いた `V7/V`・`subV7/V`・`vii°7/V` を、同じ根音の `v` として受け取り、エンジンの綴り（`V7/v` など）に直す。
- 押しは `pushes` に和音ごとに書く（`none` / `eighth` / `sixteenth`。BL-085）。プロンプトは任意の欄として短く伝える: 前のめりの勢いが欲しいロックやポップで、小節の頭の和音を 8 分早く弾きたいときだけ、1〜2 個に使う。押しの文を長くすると、評価の night-walk（短調を期待）が長調になった（2 回続けて）ので、短く保つ。`Validate` は、数と値と、最初の和音を押さないことを検査する。評価のレポートは、押した和音を `V7^8`（16 分なら `^16`）と書く。
- ローマ数字は `I, ii, iii, IV, V, vi, vii°` と七の和音記法、長調では同主短調からの借用（`iv`, `ivm6`, `ii°`, `bVI`, `bVII` とその七の和音。♭ は `b` と書く）、短調では同主長調の `I`・`IV` とナポリの `bII`、セカンダリードミナント（`V/x`, `V7/x`）と裏コード（`subV7/x`、ADR-0023）と経過の減七（`vii°7/x`、ADR-0024）、3 度のない和音（`Vsus4`・`V7sus4`・`Isus2`・`I5` など、ADR-0025、ADR-0062）、長調のブルースの属七（`I7`・`IV7`、ADR-0026）を許可し、`intent.Validate()` で検証する。書き方が調の和音と食い違うラベル（旋法やブルースを狙ったもの）は、「`IV` は D minor では Gm（`iv`）になる」と伝えて再試行させる。検証に落ちたら、その答えを assistant 発言として、検証エラーを user 発言として足し、1 回だけ再試行する（`ideas.Service`）。返事と理由の文に書かれた和音の主張が、その候補の和音と合わないときも同じく再試行する（ADR-0034）。照合するのは、ローマ数字のすぐあとに括弧で書いた和音名（根音が、その調のその和音と同じか。`I–V–vi–IV（D–A–Bm–G）` のように並びに名前を並べたものは 1 つずつ。数が合わない並びや、名前と言葉の混ざった括弧、「の」を含む括弧（「D の V7」）は照合しない。`C/G` は分数コードとしても 2 つの名前としても読み、どちらでも合わないときだけ食い違いとする）と、「X へ（解決する・進む・戻る・滑り込む・引き込む…）」の主張（文の中で X の直前のローマ数字が、この候補で X の根音の和音へ進むか。最後の和音の次は最初の和音）。エンジンが読めないラベル、ほかの候補にしかない和音、「本来」「代わりに」のような対比の文は照合しない。進行の呼び名や候補どうしの派生関係は照合しない（評価のレビュアー、BL-172）。再試行した答えもまだ食い違うときは、失敗にせず、食い違う文だけを除いて返す（音楽は正しいので、ターンを落とさない。ADR-0034 の決定 5）。
- 理由文（`reason`）は、その候補の聴きどころの短い解説（1〜2 文の日本語）として求める。学ぶ人は「この例で聴けること」として読むので、例で鳴るもの（調・テンポ・拍子・進行・型・ノリ）だけを語らせ、鳴らない楽器やメロディには触れさせない（#128）。解説パネルの文章（和声機能・終止・リズム）はエンジンが決定論的に組み立て、LLM は関与しない。
- 評価セット（`backend/internal/ideas/evals/cases.json`）で回帰を見る。`make eval`（鍵が必要。PR に `needs-eval-cases` ラベルを付けると CI でも走る。ADR-0018。Go のテストキャッシュを使わないよう `-count=1` で走らせる。`go test`
