# 0011. ローカル実行の設定と秘密情報は、起動時の環境変数だけで渡す

- 日付: 2026-11-07
- 状態: Accepted（ADR-0008 の決定 3 のうち「`.env` で渡す」を置き換える）

## 文脈

実 LLM を使う機能をローカルで手軽に動かしたい。秘密情報の扱いは起動する人に任せたい。たとえば、暗号化した値を起動の瞬間に復号して注入する道具を、コマンドの前に付けるだけで使える形にしたい。これまでは `backend/.env` を `make dev-backend` が `source` し、compose が `env_file` で読んでいた。この形には次の問題があった。

- シェルで渡した値を、ファイルの内容が上書きした（`dev-backend`）。
- compose の `environment:` が `env_file` より優先されるので、ファイルにだけ書いた鍵はコンテナに届かなかった。
- `env_file` 経由の `PORT` がコンテナの待ち受けを動かし、ポートの割り当てとずれた。
- ファイルに書いても、コンテナの中では結局環境変数になる。安全性は上がらない。

AI エージェントのセッションからアプリを起動・操作しても、エージェントが鍵を直接読まずに済む運用にしたい（技術的な完全保証は求めず、事故で読まない程度）。

## 決定

1. リポジトリが約束するのは「設定は起動時の環境変数で受け取る」ことだけ。`make dev-backend`、`make up`、`make eval` は、どのファイルも読まない。秘密情報を注入する道具は前提にしない（`<道具> -- make up` の形でそのまま使える）。
2. `compose.yaml` は、`environment:` の `${VAR:-既定値}` でシェルの値だけを渡す。`env_file` は使わない。
3. `backend/.env.example` は、使える環境変数の一覧として残す（コピーして読ませるためのものではない）。`.env` は引き続き `.gitignore` に入れ、エージェントは読まない。
4. 開発ループはネイティブのまま残す（`make dev-backend` と `make dev-frontend`）。compose はこれまでどおり本番相当の実行（`make up`）に使う。
5. 実 LLM を使う起動は人が自分の端末で行い、エージェントは起動済みのサーバーに HTTP で触る（`make e2e`、ブラウザ操作、`curl`）。鍵があるシェルでは、値を表示するコマンド（`env`、`printenv`、`docker compose config`、`docker inspect`）をエージェントは実行しない。
6. アプリの実装（`internal/config` が環境変数だけを読み、何もなくても起動する作り）は変えない。

## 検討した選択肢

- **開発ループも compose に寄せる（bind mount と `docker compose watch`）:** ツールチェーンなしで始められ、起動経路が 1 つになる。一方で、Vite のホットリロードと Go の再ビルドがコンテナ越しになって遅くなる。`node_modules` を別ボリュームで持つなど構成が増える。手元とコンテナの 2 系統を保守することにもなる。ツールチェーンは `.tool-versions` と `make doctor` ですでにそろえられるので、今は見送る。backlog の Later に発動条件つきで置く。
- **ファイル（`.env`）を正とし、シェルで上書きできるようにする:** 手軽だが、秘密情報が平文のファイルとして残り、起動する側に扱いを任せられない。
- **Docker secrets（ファイルとして渡す）:** `docker inspect` に値が出なくなるので、より強い。ただし、アプリがファイルから鍵を読むよう変える必要がある。今は範囲外。

## 結果

- 値を渡す方法が「起動コマンドの環境変数」だけになり、どこから来た値かで迷わない。
- `backend/.env` に書いていた人は、シェルで渡すか、自分の道具で注入する必要がある。
- compose の標準仕様として、プロジェクト直下の `.env` は `${}` の展開に自動で使われる。リポジトリはこれを使わず、文書でも勧めない。
- 再検討の条件: ツールチェーンなしで開発に参加する人が出たら、compose による開発ループ（Later の項目）を入れる。鍵がログやコンテナの外に漏れる経路が見つかったら、Docker secrets を検討する。
