# 0027. フロントは nginx のコンテナ、API は Go のコンテナにし、同一オリジンの 1 つのサービスとして配る

- 日付: 2026-11-09
- 状態: Accepted（所有者の判断は #206。ADR-0008 の決定 1・3 と ADR-0022 を置き換える。移行は BL-146〜148。nginx が答えるエラーの本文は ADR-0033 による）

## 文脈

ADR-0008 は、配備先が決まっていない段階で「Go の単一バイナリがフロントを embed し、同一オリジンで配る」形を選んだ。nginx を前段に置く案は、「コンテナが 2 つになり、ローカル検証と本番の構成が分かれやすい」として採らなかった。

所有者は、#206 で次の目標を決めた。

- コンテナで動く Web アプリとして、一般公開できる構成とセキュリティ対策を備える。
- フロントは nginx とビルド済みの SPA、API は Go。コンテナを分ける。
- 当面は 1 つのサービスで、同一オリジン。nginx が SPA を配り、`/api` を Go へ渡す。
- 配備先は AWS で、第一候補は ECS on Fargate（1 つのタスクに 2 つのコンテナ）。代替は EKS。
- 今はデプロイしない。いつでもデプロイできる状態で開発し、手元と配備の差を小さく保つ。

今の構成で両立を妨げるものは、#206 の調査で 2 つ見つかった。

- Go が静的配信と embed を持つ。nginx が入ると、404・キャッシュ・MIME・SPA の振り分けの規則が 2 か所になる。
- CI のスモークと E2E が、コンテナ 1 つを前提にしている。スモークは BL-142 で 1 つのスクリプトにまとめた。

## 決定

1. **配信は 2 つのコンテナで行う。**
   - `web`: nginx とビルド済みの SPA。
   - `api`: Go。`/api` だけを答える。
   - 2 つは同じネットワークにいる（compose のネットワーク、ECS のタスク、EKS の Pod）。外に開くのは `web` だけ。
2. **同一オリジンで配る。** nginx が `/api`（`/api` と `/api/` の下）を Go に渡し、それ以外を配る。CORS は要らない。
3. **配信の規則は nginx が持つ。** Go の静的配信と embed は外す（BL-148）。
   - nginx に写すのは、ADR-0022 の規則（ファイルを指すパスは 404、画面の URL は `index.html`）、キャッシュ（`assets/` は `immutable`、`index.html`・`sw.js`・manifest は `no-cache`）、圧縮。
   - 存在しないファイルの 404 の本文は、Go と同じ JSON の封筒にする。
4. **設定は起動時の環境変数だけで渡す（ADR-0011 のまま）。**
   - `api`: 今の 4 つ（`PORT`、`LLM_PROVIDER`、`ANTHROPIC_API_KEY`、`ANTHROPIC_MODEL`）。鍵は `api` にだけ渡す。
   - `web`: `PORT` と、API の場所 `API_UPSTREAM`。Vite の開発サーバーも同じ名前を読む（BL-143）。
5. **手元の本番相当の検証は compose の 2 サービスで行う。** 開発ループは今までどおりネイティブ（`make dev-backend` と `make dev-frontend`。ADR-0008 の決定 2）。
6. **検査は 1 つのスモークで行う。** `scripts/smoke.sh` を、手元・CI・配備のあとで同じように当てる。

ADR-0008 の決定 2（開発ループ）、4（CI でイメージを作ってスモークする）、5（ツールチェーンの版）、6（設定は 12-factor）は変わらない。

## 検討した選択肢

- **A: 単一バイナリのまま（ADR-0008）。** 利点: イメージ 1 つで、手元と配備の差が最も小さい。欠点: 所有者の目標（nginx の前段、一般的な構成）と合わない。圧縮・検証子・セキュリティヘッダを Go で書き足すことになる。
- **B: 2 つのコンテナ、同一オリジン（採用）。** 利点: 配信の規則を標準のやり方で書け、ECS の 1 つのタスク・EKS の 1 つの Pod にそのまま載る。欠点: compose と CI が 2 サービスになる。nginx の設定を検査する手段（CI のスモークと E2E）が要る。
- **C: 1 つのコンテナに nginx と Go。** 欠点: プロセスを監督する仕組みが要り、distroless も捨てる。一般的な形でもない。
- **D: 静的ホスティングと API を別のオリジンにする。** 欠点: CORS と PWA のオリジンの問題が増える。ADR-0008 で採らなかった理由のまま。

## 結果

- 手元の本番相当の検証は `make up`（compose の 2 サービス）になる。Docker のない環境では、`make run`（API だけ）と Vite の開発サーバーで動かす。
- 配信の規則と検査は、nginx の設定（`deploy/nginx/`、BL-146）と `scripts/smoke.sh` に置く。
- ADR-0022 の規則は nginx が持つ。Go は `/api` だけを答え、ほかのパスは JSON の 404 にする。
- 公開に向けた安全の基準（セキュリティヘッダ、CSP、読み取り専用のファイルシステム、イメージの走査、乱用の対策）と、AWS への配備の流れは、それぞれ別の ADR で決める（#206）。
