# 0008. 本番相当の配信形態を「単一 Go バイナリ」に決め、コンテナで検証可能にする

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

ローカルで本番に近い形で検証できないと、実装がまずい箇所（ホスト名の埋め込み、環境依存の設定、配信経路の前提）が後から判明し、コンテナ化が困難になり、環境差異が広がる。先に「解くべき問い」を言語化する。

**問い**
1. ローカルで再現すべきものは何か。開発ループ（HMR、素早い Go の再実行）と、本番相当の検証（実際のビルド成果物を、配備されるのと同じ形で動かす）は別の要求である。
2. 開発と本番の差はどこから生まれるか。ビルド（`vite` dev server と `vite build`、`go run` とバイナリ）、配信（Vite のプロキシと実際の同一オリジン配信）、設定（環境変数）、秘密情報（LLM の鍵）、PWA（Service Worker は本番ビルドでしか動かない）。
3. 配備形態は何か。これが未決定だと、CORS、ベースパス、SPA のフォールバック、キャッシュヘッダのすべてが決められない。
4. ローカルで何を検証可能にするか。本番ビルドが起動して UI と API が同一オリジンで動くこと、PWA のインストール可能性、fake / 実 LLM の切り替え、CI と同じイメージが手元で作れること、通しの E2E。
5. ツールチェーンは再現できるか。Go / Node / golangci-lint の版が CI と手元（人間、AI エージェント）で一致するか。
6. コンテナが唯一の実行手段になって開発ループを遅くしないか。

**現状のアセスメント（2026-11-07）**
- 良い: フロントの API 呼び出しは相対パス（`/api/v1`）。設定は環境変数のみで既定値で起動。`PORT`、`LLM_PROVIDER` がある。JSON ログを標準出力へ。`/api/v1/health` がある。ビルド時バージョン埋め込み（`httpapi.Version`）の口がある。Service Worker は `/api/` をキャッシュしない。ホスト名の埋め込みは Vite の開発用プロキシ先（`localhost:8080`）だけ。
- 不足: 配備形態が未決定。Go サーバーは静的ファイルを配信しない。Dockerfile / compose / `.dockerignore` がない。`vite preview` は API にプロキシしないので PWA を本番ビルドで検証する手段がない。Node と golangci-lint の版は CI にしか固定されていない。通しの E2E は手動スクリプトのみ。

## 決定

1. **配備形態は単一の Go バイナリ**: API に加えて、ビルド済みフロントエンド（`frontend/dist`）を `embed` で同梱し、同一オリジンで配信する。SPA のフォールバック（`/api` 以外の未知パスは `index.html`）、ハッシュ付き資産は長期キャッシュ、`index.html` と `sw.js` は `no-cache`。CORS は不要。
2. **開発ループは native のまま**: `make dev-backend` と `make dev-frontend`（Vite のプロキシ）。コンテナは開発ループの手段にしない。
3. **本番相当の検証はコンテナで**: マルチステージの Dockerfile（Node でフロントをビルド → Go でバイナリをビルド → 最小ランタイム、非 root、`HEALTHCHECK`）と `compose.yaml`（`docker compose up` で http://localhost:8080 に UI と API）。`.env` で `LLM_PROVIDER` と鍵を渡す。
4. **CI でイメージをビルドしてスモークする**: Dockerfile の腐敗を防ぐ。通しの E2E（Playwright）はこのイメージに対して走らせる。
5. **ツールチェーンの版を 1 箇所に固定する**: `.tool-versions`（Go、Node、golangci-lint）を CI と `make doctor` が読む。
6. **設定は 12-factor のまま**: 新しい設定は `internal/config` と `.env.example` に追加し、ホスト名やポートをコードに書かない。

## 検討した選択肢

- **フロントは静的ホスティング、API は別サービス**: スケールや CDN には有利だが、CORS・2 つの配備・PWA のオリジン問題が増え、学習用アプリの規模に合わない。再検討の条件: 静的配信の遅延やコストが問題になったとき。
- **compose で dev ループも提供（bind mount + ホットリロード）**: ツールチェーン不要で始められるが、遅く、壊れやすい。代わりに `.tool-versions` と `make doctor` で版を揃える。必要になれば devcontainer を検討する。
- **Go 側で静的配信せず Nginx を前段に置く**: コンテナが 2 つになり、ローカル検証と本番の構成が分岐しやすい。単一バイナリの方が差異が小さい。

## 結果

- 配備は「イメージ 1 つ、環境変数いくつか」で済む。ローカルの `docker compose up` が本番と同じ経路で動く。
- フロントのビルド成果物をバックエンドに同梱するため、`make build` の順序（vite build → copy → go build）が決まる。開発時は同梱なしでも API だけで起動できなければならない。
- 再検討の条件: 上記の静的ホスティングの条件、またはサーバー側の永続化やマルチユーザー（M4 以降）で構成が増えるとき。
