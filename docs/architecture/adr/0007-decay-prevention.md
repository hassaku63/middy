# 0007. 開発サイクルの劣化を、矯正・検知・削減の三層で防ぐ

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

AI エージェントが自律的に開発を回すと、各 PR は規約に適合していても、小さく正しい変更の積み重ねで全体が劣化する。原因は四つ。(1) エージェントは「`make check` が緑」への最短経路を取るので、境界の曖昧な依存や肥大するファイルは 1 件ずつでは指摘されない。(2) 文章だけのルールは、セッションをまたぐエージェントには毎回「初見の願望」で、守られたかを誰も検証できない。(3) 追加は backlog と docs-sync で統制されるが、不要になったコード・テスト・依存を消す圧力がない。(4) エージェントの生産量に対して人間のレビューは増えないので、未レビューのまま溜まるか、見ずにマージするかになる。守る側のハーネス自体も、検査が増えると遅く・うるさくなり迂回される。

## 決定

1. **AGENTS.md の各ルールは、機械的に強制されるか、定期監査の対象であるかのどちらかでなければならない。** どちらでもないルールは書かない。既存の願望（feature 間 import 禁止、PR 400 行、副作用の配置）には仕掛けを付ける。
2. **矯正（やりにくくする）**: アーキテクチャ境界を lint にする（Go は `depguard`、TS は `no-restricted-imports` と `no-restricted-globals`）。関数・ファイル・PR にサイズと複雑度の予算を置く。副作用はコンポーネントに書けないようにする。
3. **検知（傾向を見る）**: テストの所要時間と合計を毎 CI で出し、予算を置く。CI 合計時間に予算を置く。月次 gardening を backlog の老化と flaky の集計に広げる。`music` が十分に育ったらミューテーションテストで「何も検出しないテスト」を見つける。
4. **削減（溜まったものを捨てる）**: `go mod tidy -diff`、`npm audit`（本番依存のみ）、`govulncheck` を CI に。未使用 export・ファイル・依存は閾値到達後に `knip` を導入する。ハーネスの全検査を ハーネス一覧文書（`docs/dev/` 配下、BL-032 で作る） に一覧し、四半期の見直しで「捕まえた実績がなくコストだけの検査」を削る。
5. **レビュー処理能力**: エージェントは未マージ PR が 3 本になったら止まり、人間に判断を仰ぐ。PR にリスク区分と「レビューの見どころ」を必須化する。PR を開く前に自己レビュー（`/code-review`）を行い、要約を PR に貼る。
6. **言語またぎの整合**: バックエンドが正準フィクスチャ（記号・ローマ数字・分析済みタイムライン）を生成し、フロントのテストがそれで `notation` 等を照合する。OpenAPI → TS 型生成はエンドポイント 5 本で発動する。
7. **閾値で発動する仕掛け** は backlog の Later に「発動条件」つきで置く: `knip`（最初の feature 削除）、ミューテーション（`music` 3k 行）、型生成（5 エンドポイント）、バンドル予算と描画計測（BL-025）、プロンプト監査（BL-011 以降、四半期）。

## 検討した選択肢

- **規約と PR テンプレートだけ**: コストはゼロだが検証できない。却下（現状がこれ）。
- **カバレッジ目標**: 数値を目標にすると無意味なテストが増える。`music` の床（90%）だけを維持し、他は所要時間とミューテーションで見る。
- **LLM による PR ごとの構造監査**: 意味的なズレを拾えるが、決定論的検査で拾える構造的な崩れをまず潰す。自己レビューは PR 作成者側の手順に留める。

## 結果

- lint と予算は最初は緩く設定し、引っかかった箇所を「設計を変える合図」として扱う（`App.tsx` が最初に当たる想定）。
- 検査の追加はハーネスのコストでもあるため、ハーネス一覧文書（`docs/dev/` 配下、BL-032 で作る） の一覧なしに検査を足さない。
- 再検討の条件: 月次 gardening の指摘が 3 か月連続でゼロなら検知の閾値を見直す。CI が 10 分を超えたら検査の分割か削減を行う。
