# 0061. 表せなかったものを、本番の答えでも求めて要約の下に出す

- 日付: 2026-11-11
- 状態: Accepted（所有者の判断は Issue #450 の A。ADR-0013 の「この欄は本番の要求に入れない」を置き換える）

## 文脈

ADR-0013 は、評価のときだけ AI に「指示された語彙やカタログで表せないために使わなかったもの」（`unconstrained`）を書かせ、「表せない」と「選ばない」を切り分けた。本番の要求には入れていなかった。

外部のレビュー（#447）で、「要求をどう反映したかが分かりにくい」と指摘された。たとえば sus2 やソウルを頼んでも、アプリの語彙にないので、AI は近いもので置き換える。ユーザーには、置き換えたことが見えない。所有者は、表せなかったものを要約の下に小さく出すと決めた（#450 の A）。

## 決定

1. `intent.Schema` に、省略できる `unconstrained`（文字列）を常に入れる。説明は、ユーザーに見せる 1 文として書かせる（表せなかったものと、代わりにどう近づけたか）。なければ「なし」。評価専用の `DiagnosticSchema` と `ideas.NewDiagnostic` はなくし、評価も本番と同じ要求で測る。
2. サービスは「なし」と空白を空として扱い、API の `IdeasResponse.unconstrained` に、あるときだけ載せる。音にも検証にも使わない（ADR-0003 の境界は変わらない）。
3. 画面は、返答の要約のすぐ下に、小さく控えめな色で「この例では表せなかったもの（AI の見立て）: …」と出す。空なら出さない。次のターンの履歴には入れない。

## 検討した選択肢

- A: 本番でも求め、要約の下に出す（採用）。利点: 置き換えたことがユーザーに見える。評価と本番の要求が同じになり、測ったものが本番の振る舞いになる。欠点: 毎回の出力が 1 文ぶん増える。AI の自己申告なので、正しいとは限らない。
- B: 評価専用のまま、要約の文に置き換えたことを書かせる。利点: API と画面を変えない。欠点: 要約の文の規則が増え、書くかどうかが揺れる。表示を分けられず、控えめに見せられない。
- C: エンジンが表せない語彙を決定論的に検出する。利点: 自己申告に頼らない。欠点: 依頼の言葉から「表せないもの」を読むには、言葉の解釈が要る。それは LLM の担当（ADR-0003）。

## 結果

- ユーザーは、例が依頼のどこを表せていないかを読める。表示の言葉は「AI の見立て」として控えめにする。
- 評価の「表せないために使わなかったもの」の表は、本番と同じ要求から作られる。説明の文が評価専用からユーザー向けに変わるので、絞った評価で書きぶりを確かめる。
- 書きぶりが長い、または的外れが多いと分かったら、説明の文を直すか、表示を折りたたむ。
