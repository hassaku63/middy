# 0039. 全件の評価を、Message Batches で送れるようにする

- 日付: 2026-11-10
- 状態: Accepted（所有者の判断は #334）

## 文脈

実 API の評価（ADR-0018）は、全件で答え 44 件と出し直し、レビュアー 44 件、合わせて約 100 回の呼び出しをする。どれも急がない（PR のコメントとして読む）。Anthropic の Message Batches は、まとめて送った要求を非同期に処理し、料金は 1 件ずつ送るときの半分になる。ただし答えは数分から、遅いと 1 時間を超えて返る。所有者は #334 で、全件の評価ならバッチを採用し、5〜10 件なら今の 1 件ずつでよい、と決めた。

## 決定

1. **`anthropic.Batcher` を足す。** `llm.Client` を満たし、ほぼ同時に来た要求をまとめて 1 つのバッチで送る。次の要求が来ないまま一定時間（評価では 10 秒）待ったら送り、終わるまで問い合わせ（30 秒ごと）、答えを呼び出し元ごとに返す。バッチを送ったあとに来た要求（答えを見たあとの出し直し）は、次のバッチに入る。答えの読み方（使用量、拒否、打ち切り）は 1 件ずつのときと同じ関数で読む。
2. **評価は、バッチのときはすべてのケースを同時に送る**（`RunTogether`、`ReviewAllTogether`）。最初の 1 件を単独で送る今の方法（キャッシュを書かせるため）や、4 件ずつの並行では、バッチが 1 件や数件になってしまう。
3. **`EVAL_BATCH` で切り替える。** `1` は常にバッチ、`0` か空は 1 件ずつ、`auto` はケースが `EVAL_BATCH_MIN`（既定 20）件以上のときだけバッチにする。少ないケースは、どちらで送っても費用の差が小さく、1 件ずつの方が速い（所有者の判断、#334）。報告の末尾に、どちらで送ったかを書く。時間がかかるので、`make eval` の時間切れを `EVAL_TIMEOUT` で延ばせるようにする。CI の全件（`needs-eval`）で使うかどうかと、ジョブの時間切れは `eval.yml` の変更になるので、所有者のレビューを経て別に決める。
4. **バッチでは、システムプロンプトを 1 時間キャッシュする。** バッチの割引とキャッシュの割引は重なるが、バッチの中のキャッシュの当たりはベストエフォートで、バッチは 5 分を超えうる。公式のドキュメント（Batch processing の「Using prompt caching with Message Batches」）が、共有する文脈には 1 時間のキャッシュを勧めている。1 件ずつのときは今までどおり 5 分。
5. **アプリ本体（`/ideas`）には使わない。** 学ぶ人は答えをその場で待つ。

## 検討した選択肢

- A: 呼び出し元を変えずに、クライアントの側で集める（採用）。利点：出し直しや理由の文の検査（ADR-0034）を含む今の流れが、そのまま 2 回目以降のバッチになる。欠点：呼び出し元が同時に要求しないと集まらない（2 の決定で解く）。
- B: 評価の側で、答えの 1 回目・出し直し・レビュアーを、それぞれ明示的にバッチにする。利点：何がいつ送られるかが見える。欠点：出し直しの判断が `ideas.Service` の中にあるので、評価のために流れを複製することになる。
- C: バッチにしない。欠点：全件の費用が半分にならない。

## 結果

- 全件の評価の単価が半分になる見込み。実際の差は、評価の報告の「API の使用量」で比べる（料金表の割引は入出力の token 数には出ないので、token 数そのものは変わらない）。
- 全件の評価は、結果が返るまで数分から 1 時間ほどかかりうる。PR の評価を急ぐときは、絞った評価（ADR-0038）を使う。
- システムプロンプトのキャッシュは、バッチでも読まれるが、1 件ずつのときより当たりにくいことがある。当たり具合は、報告の「API の使用量」のキャッシュの読み書きで確かめる。当たらない分は入力が割引前の半額で課金されるので、出力（考える分を含む）に比べて入力が大きい場合は、バッチの得が小さくなる。1 件ずつの全件とバッチの全件の数字を比べて、`auto` の閾値や使い分けを見直す。
