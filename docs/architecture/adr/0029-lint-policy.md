# 0029. 推奨される lint は 1 つずつ入れ、道具そのものの陳腐化を定期的に検討する

- 日付: 2026-11-09
- 状態: Accepted（所有者の判断は #226。ADR-0007 の矯正と削減を広げる）

## 文脈

整形・型・構造は機械が止めている（`docs/dev/harness.md`）。ただ、言語やフレームワークの世の中の慣例を守らせる lint は、各道具の推奨の設定に乗っているだけだった。名の通ったルールのうち、入っていないものが多い（#226 の候補の表）。

開発は主に AI が進める。AI が「よい書き方」を選ぶ拠り所は、記憶ではなく機械の検査に置きたい。一方で、lint の道具そのものも古くなり、新しい道具も現れる。依存が増えすぎるのも避けたい。

## 決定

1. **推奨される lint は、できる限り入れる。**
2. **1 つの linter（または 1 つのプリセット）を、1 つの PR で入れる。** 指摘はその PR の中で全部直し、どの道具が由来かを分かるようにする。
   - 400 行を超えそうなら、同じ linter のままディレクトリで分ける。
   - 指摘が 0 件の linter は、まとめて 1 PR にしてよい。
3. **依存の予算。**
   - 今の道具に同梱のもの（golangci-lint の linter、typescript-eslint のプリセット）を先に使う。
   - 新しい依存は、十分に枯れていて、頻繁にメンテナンスされているものに限る。依存を足す PR の本文に、一次情報（npm レジストリ、GitHub のリリース）で確かめた次の根拠を書く。
     - 最初の公開からの年数
     - 最後の公開の日付
     - 直近 1 年の公開の回数
     - 週あたりのダウンロード数
     - メンテナの体制
   - 満たさない候補は入れず、代わりの案を企画にする。
4. **除外には理由を書く。** `//nolint:<linter> // 理由`、または設定での除外に理由を書く。`nolintlint` が、理由のない除外を落とす。
5. **道具の陳腐化を、四半期ごとに検討する。**
   - 決定論の報告: 定期のジョブが Issue を開くか更新する。対象は、deprecated の依存、長く公開のない依存、非推奨のルールの使用、`harness.md` の四半期の見直し。
   - AI による検討: その Issue を入力に、Claude の定期のタスクが、新しい道具やスタックを一次情報で調べ、企画にする。実装はしない。

## 検討した選択肢

- **A: 推奨を 1 つずつ入れ、定期的に見直す（採用）。** 利点: 指摘の由来が PR ごとに分かる。道具の陳腐化にも追従する。欠点: PR の数が多い。
- **B: まとめて入れる。** 欠点: 差分が大きく、どの指摘がどの道具から来たかが分からない。レビューできない。
- **C: 今のまま。** 欠点: 慣例からのずれを機械が見ない。AI の記憶に頼る。

## 結果

- 候補と順序は #226 のスライスの表。backlog に写した。
- lint を足すたびに、`harness.md` の表に 1 行足す（ADR-0007）。
- 四半期の見直しで、捕まえた実績のない lint は削除の候補にする（ADR-0007 のまま）。
