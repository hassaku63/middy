# 0006. ドキュメントは現在の状態だけを書き、機械的検査と定期点検で鮮度を保つ

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

middy は AI エージェントが長期間、自律的に開発サイクルを回すことを前提にしている。エージェントはセッションをまたいで記憶を持たず、リポジトリ内の文書を信じて動く。文書が古くなったり、過去の経緯が散在したりすると、それは AI と人間の両方にとって情報ノイズになり、誤った前提で実装が進む。

M0 の時点で既に、カバレッジの数値、「予定」の一覧、ロードマップの進捗マークなど、放置すれば確実に腐る記述が複数あった。人力のチェックリストだけでは維持できない。

## 決定

1. **文書は現在の状態だけを書く。** 経緯は git log と ADR にだけ残す。ADR は追記のみで、Superseded にするときは影響する「現在」の文書を同じ PR で直す。
2. **事実は 1 箇所に置き、他は参照する。** 進捗は backlog、API は OpenAPI、設定は `.env.example` と `config`。数値・日付・「予定」リストはコピーしない。将来の話は BL-ID で指す。
3. **決定論的な検査を `make check` と CI に組み込む。** リンク切れ、存在しないパス、索引漏れ、存在しない BL-ID（`scripts/check-docs.sh`）。登録ルートと OpenAPI の一致（Go テスト）。
4. **開発ループに自己点検を組み込む。** PR 前に差分から文書を逆引きする `docs-sync` 手順を標準化し、PR テンプレートのチェック項目にする。
5. **月次の庭仕事を自動化する。** GitHub Actions の cron が検査と鮮度レポートを走らせ、指摘があれば Issue を 1 つ立てる。
6. **backlog の Done 表は直前のマイルストーンまでしか残さない。** 古い ID への参照が検査で落ちることを、文書の見直しトリガーとして使う。

## 検討した選択肢

- **PR テンプレートと規則だけ（現状）**: コストゼロだが、守られたかを誰も検証できない。却下。
- **LLM による PR ごとの自動監査（GitHub Action）**: 意味的なズレを拾えるが、API キーとコストが要り、誤検知の扱いも設計が必要。まず決定論的検査で「構造的に壊れた参照」を潰し、LLM 監査は `docs-sync` を手動またはサブエージェントで行う形に留める。月次の指摘量を見て自動化を再検討する。
- **文書を生成物にする（コードから自動生成）**: ルート一覧や型の表は将来の候補。現時点では文書量が少なく、検査で十分。

## 結果

- 構造的に壊れた文書（存在しないパス・ID・リンク）はマージできなくなる。
- 「予定」や数値を書けなくなるため、文書は短くなり、backlog の役割が重くなる。これは意図どおり。
- 検査は語彙に依存する（バッククォートで囲まれたパス、`BL-NNN` 形式）。この規約を守らない書き方は検査をすり抜けるので、規約自体を `docs/dev/docs-hygiene.md` で明示する。
- 再検討の条件: 月次 Issue に意味的なズレ（検査では拾えない誤り）が繰り返し出るなら、LLM 監査の定期実行を ADR で検討する。
