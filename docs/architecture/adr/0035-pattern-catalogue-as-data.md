# 0035. 型のカタログは、版管理され検証されるデータとしてエンジンに含める

- 日付: 2026-11-10
- 状態: Accepted（所有者の判断は #207）

## 文脈

伴奏・ドラム・スタイルの型（カタログ）は、`internal/music/pattern` の Go の表だった。型を 1 つ足すにも Go の構造体リテラルを書くことになり、音楽の知識を持つ人が型を書く入口として重い。決まり（id の重複、打の位置、拍子、スタイルが名指す型の存在）は、テストに散らばっていた。

ADR-0003 は、音符・和音・分析をエンジンが作り、LLM は解釈と対話を担うと決めている。カタログをデータにしても、この境界を崩してはならない。

## 決定

1. **カタログを JSON にする。** `internal/music/pattern/data/` の `accompaniments.json`・`drums.json`・`styles.json`。打は 1 行に 1 つ書く。`embed` で読み、依存は足さない。
2. **カタログはエンジンの一部である。** ファイルはコードと同じく版管理し、PR でレビューする。実行時に外から差し替えない。LLM が書き換えることもない。ADR-0003 の境界は変わらない。LLM は今までどおり、カタログの id を選ぶだけ。
3. **起動時に全体を検証する。** `pattern.Catalogue.Validate` が決まりをすべて一度に返す。壊れていれば起動しない。決まりは次のとおり。
   - id の重複がない。名前・説明・打がある。
   - 拍子が、エンジンの描ける拍子である。
   - 打が小節に収まる。音高・強さ・声部が正しい。
   - スタイルが名指す型が存在する。block 以外の型は、どれかのスタイルに属する。
   - 楽器は、番号と名前を対で書く。

   JSON は、未知の項目を拒んで読む。
4. **変わらないことをゴールデンで守る。** 描画の結果、`GET /patterns`、システムプロンプトをゴールデンファイルで固定する（BL-176）。カタログの移行で、これらは 1 バイトも変わらない。

## 検討した選択肢

- A: JSON にして embed で読む（採用）。利点: 依存がない。標準ライブラリで厳密に読める。`GET /patterns` と同じ形になる。欠点: コメントが書けない。説明は `description` に書く。
- B: YAML。利点: 読みやすく、コメントが書ける。欠点: パーサーの依存が要る。値の解釈が曖昧になりやすい（`no` が偽になる、など）。
- C: Go の表のまま。利点: 型の検査がコンパイラで効く。欠点: 型を書く入口が重い。決まりがテストに散らばる。

## 結果

- 型を足すときは、JSON に 1 項目足し、`go test ./internal/golden -update` で描画のゴールデンを書き直して、差分を PR で見せる。
- カタログの決まりは `Validate` の 1 か所にある。決まりを変えるときは、`Validate` とそのテストを直す。
- 型を書く人のための足場（JSON Schema、「型の足し方」）は BL-180。
- 実行時にカタログを読み替える要求（ユーザーが型を足す、など）が出たら、境界を見直す。そのときは ADR を書き直す。
