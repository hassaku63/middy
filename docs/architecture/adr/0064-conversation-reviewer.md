# 0064. 会話の査読は、会話 1 本を通して読み、依頼に従ったかを 4 つの区分で数える

- 日付: 2026-11-12
- 状態: Accepted（所有者の判断は Issue #473 の A。採り入れる程度の幅は ADR-0065）

## 文脈

実際の使い方に近い品質を見るため、利用の型ごとの台本で会話を集めるようにした（#473、BL-314）。台本には、決定的に数えられる期待（拍子・小節数・調の種類・テンポの向き・含む語）を書ける。

ただ、言い直しの品質の多くは数えられない。次のようなことは、言葉の意味を読まないと分からない。

- 「もう少し明るく」が反映されたか。
- 前の回に決めた条件が、頼んでいないのに消えていないか。
- 「2 番目の例をもとに」が通じたか。
- 返事が言う変更点が、中身と合っているか。

既存の独立したレビュアー（`evals/review.go`、ADR-0034）は、依頼 1 文と答え 1 つだけを読み、理論の誤りを数える。前の回との関係は見ない。

## 決定

1. **会話 1 本を通して読む査読を足す（`converse judge`）。** `collect` が残した run の JSON を読み、会話 1 本につき 1 回、査読のモデルに渡す。渡すのは、回ごとのユーザーの言葉、返事、候補ごとの調・拍子・テンポ・小節数・和音の並び（ローマ数字と鳴る和音名）・型・理由の文。台本の期待は渡さない。答えを、作る側の期待ではなく、ユーザーの言葉と照らして読ませるため。
2. **数えるのは 4 つの区分だけにする。**

   | 区分 | 中身 |
   | --- | --- |
   | 1 反映されていない | その回に頼んだ変更が、どの候補にも入っていない（一部の候補に入っていれば数えない） |
   | 2 頼んでいないのに変わった | 前の回までに決めたことが、頼んでいないのにすべての候補で失われた |
   | 3 指した例の取り違え | 特定の例を指したのに、別の例をもとにした |
   | 4 返事が変更点を誤って言う | 返事や理由の文が言う変更が、候補の中身と合わない |

   - 区分 1 は、頼んだものが候補のどれにも「まったく」入っていないときだけ数える。
   - 採り入れる程度の幅（ADR-0065）は数えない。代わりに、幅を使ったところを「幅の内」として別に返させ、件数に入れずに一覧で見せる。種類は、程度が小さい・一部だけ・「全部」と言われたが一部・初心者向けの単純化。
   - 区分 4（返事が変更点を誤って言う）は幅の外。言ったことと中身が違えば数える。
   - 理論の誤りは数えない。ADR-0034 のレビュアーが見る。
   - 同じ依頼から違う答えが出ること、好みの違いも数えない。
   - 表せない語彙で近いものに置き換えたことを返事で断っていれば、数えない。
   - 確信が持てないものは数えない。
3. **報告だけにする。** 合否には使わない。会話は揺れが大きく、査読の確かさもまだ分からない。合否にするかは、所有者の採点（BL-317）との一致を見てから考える。
4. **鍵を持つのは `judge` だけ。** `collect` は鍵のないクライアントのまま。`judge` はサーバーと同じ設定（`LLM_PROVIDER`、`ANTHROPIC_API_KEY`、`ANTHROPIC_MODEL`）を読む。fake では、すべての会話が「指摘なし」になり、鍵なしで通しを試せる。

## 検討した選択肢

- A: 会話 1 本を通して 1 回で読む（採用）。利点: 前の回との関係（区分 2・3）が読める。呼び出しは会話の数だけ。欠点: 会話が長いと入力が大きい。今の台本は 3〜5 回なので収まる。
- B: 回ごとに、前の回と今の回の 2 つだけを読む。利点: 入力が小さい。欠点: 2 回より前に決めた条件が消えたことに気づけない。呼び出しが回の数だけ増える。
- C: ADR-0034 のレビュアーに区分を足す。利点: 仕組みが 1 つで済む。欠点: あちらは答え 1 つを読む設計で、会話の文脈を渡すと理論の査読の焦点がぼける。

## 結果

- 決定的に数えられない言い直しの品質が、区分ごとの件数と指摘の一覧で読める。
- 指摘は仮説で、当否は所有者が見る。甘い・揺れるなどの問題が見えたら、区分の定義を直す。
- CI から流すのは BL-316 で、鍵を渡すステップの中で `judge` を走らせる。
