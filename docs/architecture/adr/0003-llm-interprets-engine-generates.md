# 0003. LLM は解釈、理論エンジンが生成

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

プロダクトの中核は「イメージを AI で解釈し、合うパターンを提示し、再生でき、成り立ちを解説する」こと。LLM に MIDI/音符を直接書かせる案と、LLM はパラメータだけを出し音符は決定論的に作る案がある。

## 決定

- LLM の出力は **`MusicalIntent`（構造化 JSON）** に限定する: 調候補、モード、テンポ範囲、雰囲気タグ、進行テンプレート候補（ローマ数字）、理由文。
- 音符・ボイシング・リズム・分析（ローマ数字、和声機能、ケーデンス）は **`backend/internal/music` の純粋関数** が生成する。
- LLM の出力は必ず `intent.Validate()` で理論的妥当性を検証してからエンジンに渡す。
- 解説の「事実」はエンジンの分析結果であり、LLM は言い換え・補足にのみ使う。

## 検討した選択肢

- **LLM が音符を書く**: 柔軟で多彩だが、同じ入力で結果が変わり、理論的に誤った出力を検証する手段がなく、解説と音が食い違う。トークンコストも高い。
- **LLM が理論エンジンを tool として呼ぶ**: エージェント的で魅力的だが、M2 の要件（候補 2〜3 個）には過剰。将来、相談の高度化で必要になれば ADR で再検討。

## 結果

- 再現性があり、fake LLM で end-to-end テストが書ける。CI にネットワークが不要。
- 表現の幅はパターン辞書の広さに縛られる。これは **意図的** で、学習者向けには「理論で説明できる範囲」に収まることが価値になる。
- `music` パッケージの充実（進行テンプレート、パターン、分析）がプロダクトの表現力そのものになるため、backlog では M1 を LLM なしで先行させる。
