# 0032. main への push でも、変わったところに関係するジョブだけを走らせ、その実行は取り消さない

- 日付: 2026-11-09
- 状態: Accepted（所有者の判断は #266 の A。ADR-0016 の決定 4 と ADR-0028 の決定 4 の、push の扱いを変える）

## 文脈

PR の CI は `scripts/ci-changes.sh` で、変更に関係するジョブだけを走らせている（ADR-0016 の決定 4）。`main` への push では、変更に関係なく全部が走っていた。文書だけの PR でも、マージのたびに backend・frontend・image が走り、push の実行は 1 本あたり約 8 分かかる（#266 の測定）。

`main` の実行は、次の push で取り消されていた（`cancel-in-progress: true`）。連続でマージすると、前のコミットの `image` は最後まで走らない（run 598）。ADR-0028 の決定 4 は「`image` は `main` への push で毎回走るので、壊れても気づける」としていたが、連続でマージすると成り立っていなかった。

## 決定

1. **`main` への push でも、`ci-changes.sh` でジョブを選ぶ。** 比べる相手は、push の前の `main` の先頭（`github.event.before`）。PR と同じ規則を使うので、PR で走らなかったジョブは `main` でも走らない。`.tool-versions`・`Makefile`・`scripts/`・`ci.yml` の変更では、今どおり全部が走る。
2. **前の先頭が取れないとき（新しいブランチ、履歴にないコミット）と、手動の実行では全部を走らせる。**
3. **`main` の実行は取り消さない。** push ごとに別の同時実行のグループにする。各実行はその push の差分しか見ないので、取り消したり置き換えたりすると、その差分が検査されずに残る。PR では今どおり、新しい push が古い実行を取り消す。
4. **ベースイメージの変化には、週 1 回の e2e（`e2e.yml`、イメージを作る）で気づく。** `image` は `main` で毎回は走らない。

## 検討した選択肢

- A: push でも差分で選び、`main` の実行は取り消さない（採用）。
- B: PR で検証した結果と同じ木なら、push の CI を全部飛ばす。欠点: 必須チェックは `strict` でない（ADR-0028 の決定 6）ので、古い `main` で検証したままマージされうる。同じ木かどうかの判定も複雑になる。
- C: 今のまま（push では全部、取り消しあり）。欠点: 文書だけのマージでも約 8 分かかり、連続マージでは `image` が最後まで走らない。

## 結果

- 文書だけのマージでは、`main` で backend・frontend・image が走らない。
- `main` の各コミットは、そのコミットで変わったところに関係するジョブを最後まで走らせる。連続でマージすると、同時に走る実行が増える。
- `main` で失敗したジョブは、次の push では、同じところに触れない限り走り直さない。失敗はそのコミットの実行に残るので、そこで直す。
- パスの規則に漏れがあると、PR と同じく `main` でも検査が漏れる。漏れが見つかったら `ci-changes.sh` を直す。
