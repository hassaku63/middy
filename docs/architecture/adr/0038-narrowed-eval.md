# 0038. 評価を、タグで絞って走らせられるようにする

- 日付: 2026-11-10
- 状態: Accepted（所有者の判断とレビューは #334）

## 文脈

実 API の評価（ADR-0018）は、`needs-eval` を付けるたびに全ケース（44 件）と、独立したレビュアー（BL-172）を走らせる。ケースと評価を付ける PR が増え、API キーのクレジットを使いやすくなった（#334）。一方で、多くの PR が変えるのは 1 つの観点だけだ。たとえば #328 の拍子、#331 の分数コード、#327 のスタイル。所有者は、検証の効き目をできるだけ保ったまま費用を抑えたい、と言っている。

## 決定

1. **ケースに、何を見るかのタグを付ける**（`evals.Tags`: smoke・basic・mode・meter・style・groove・chords・slash・tension・named）。どのケースにもタグを 1 つ以上付け、どのタグにもケースを 1 つ以上置く（テストで検査）。
2. **`EVAL_TAGS` で、そのタグのケースだけを走らせる。** 知らないタグは誤りにする（0 件で通らないように）。表の末尾に、評価したケースを書く。
3. **CI では、ラベル `needs-eval:<tag>` が、そのタグと `smoke` のケースだけを走らせる。** `needs-eval` は今までどおり全件。ラベル名は data として読み、小文字の 1 語だけを通す。

## 検討した選択肢

- A: タグとラベル（採用）。利点：作者が観点を選べて、仕組みが小さい。欠点：どのタグを選ぶかは作者の判断で、思わぬ回帰を見逃しうる（`smoke` で一部を補う）。
- B: 変更のゴールデンの差分から、走らせるケースを自動で決める。利点：選び忘れがない。欠点：差分と観点の対応表の保守が要り、大きい。
- C: 既定（`needs-eval`）を絞った版にし、全件は `needs-eval:full`。利点：ふだんの費用がいちばん下がる。欠点：既定を変えるのは運用の判断なので、所有者が決める（#334）。

## 結果

- 1 つの観点を変えた PR は、全件の数分の 1 の費用で測れる。1 回の費用は、評価の報告の「API の使用量」で比べられる（#334 のスライス 1）。
- 全件をいつ走らせるか（節目、プロンプトの大きな変更）と、エージェントがどのラベルを付けるかの規則は、#334 で所有者が決める。
- タグを足すときは `evals.Tags` と cases.json を同時に直す。
