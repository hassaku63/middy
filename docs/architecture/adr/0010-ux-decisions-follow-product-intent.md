# 0010. UI の判断は、プロダクトの意思を根拠に共通の原則と手順で行う

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

UI は機能を足すたびに要素が増え、画面の判断に拠り所がなかった（保存欄の常時表示が BL-060、解説とタイムラインの分離が BL-061）。引き算の原則は一般にあるが、原則どうしは衝突し、どちらを取るかは原則からは決まらない。判断には、プロダクトが何を優先するかという意思が要る。

## 決定

1. UI の判断を、意思・概念・流れ・画面の約束・実装の層で行い、下の層は上の層を根拠にする（[UI/UX 設計の原則と手順](../../design/ux-principles.md)）。
2. 共通の原則と、新しい画面や操作を決める手順をその文書に置く。プロダクト固有の中身は `docs/product/` に置く。
3. 意思は「X を Y より優先する」の形で書き、持ち主が決める。エージェントは推論した案を仮として書いて進めてよく、迷う点は持ち主に返す。
4. UI を変える PR には、手順の各段階を数行で添える。

## 検討した選択肢

- 個別の不具合として直す: 速いが、次の機能で同じ散らかりが起きる。
- 見た目のデザインシステムから作る: 何を残すかの判断には効かない。
- 原則だけを書く: 衝突を解けず、判断がその場の好みに戻る。

## 結果

- 画面の要素ごとに、なぜあるかを上の層までたどって問えるようになる。たどれない要素は削る候補になる。
- 意思が書かれるまでは、UI の大きな変更は仮の意思に依存する。
- PR テンプレートの確認項目は人のレビューで見る。機械的な検査（初期画面の操作要素の数など）は backlog の Ideas に置き、必要になったら入れる。
- 再検討の条件: 手順を添えた UI の PR が、意思や概念を参照せずに書かれ続けるようなら、手順を簡略化するか検査を入れる。
