# 0014. 観察と企画を GitHub Issue に置き、backlog と ADR はそのまま正典に保つ

- 日付: 2026-11-08
- 状態: Accepted

## 文脈

開発の記録は 3 か所にある。`docs/product/backlog.md`（並びと状態）、ADR（設計の判断）、PR（変更そのもの）。一方で、次のものには置き場がなかった。

- **観察**: 使っていて、レビューしていて、評価して見つけたこと。「B♭ major が A# と出る」「同じ短調の循環が多い」「ジャズの和声に 8 ビートが付く」。これまでは会話で報告され、会話で消えた。
- **検討**: 観察から問題を理解し、事実を確かめ、選択肢を比べ、推奨を出す過程。ADR-0012 と ADR-0013 の分析は、ADR に書くまで会話にしかなかった。
- **所有者の判断待ち**: 「決めてほしいこと」を会話で尋ね、会話で答えをもらっていた。セッションは使い捨てで、次のセッションからは見えない。何が未決かを一覧する手段もなかった。

所有者の意向は、AI が検討を揉み、その結果の企画が Issue になる形。GitHub Issue はすでに月次の庭仕事（`docs-gardening`）が使っている。「機能スライス」の Issue テンプレートがあったが、使われていなかった（スライスは backlog にある）。

守るべき制約は ADR-0006 の「事実は 1 か所にだけ書く」。Issue が backlog の状態や ADR の判断を重複して持つと、どちらが正しいか分からなくなる。

## 決定

1. **Issue は 2 種類。ラベルで区別する。**

   | 種類 | ラベル | 何を書くか | いつ・誰が |
   | --- | --- | --- | --- |
   | 観察 | `observation` | 見たこと、どこで（版、実 LLM か fake か）、補足。原因や解決策はなくてよい | 見つけたときすぐ。所有者でもエージェントでも。所有者が会話で報告したことは、エージェントが Issue に写す |
   | 企画 | `proposal`（判断待ちの間は `needs-decision` も） | 問題、事実と推測、選択肢、推奨、決めてほしいこと、スライス案、文書への影響 | エージェントが `/propose` の手順で検討した結果。所有者は「決めてほしいこと」にコメントで答える |

   月次の `docs-gardening` はそのまま 3 つ目の種類として残る。

2. **正典は動かさない。** 並びと状態は backlog だけが持つ。設計の判断は ADR だけが持つ。Issue はその手前の「観察 → 検討 → 判断待ち」を受け持つ。
   - 企画のスライスが決まったら、backlog に写し、行の見出しに `(#N)` を添える。状態は backlog でだけ更新する。
   - 設計の判断が要る企画は ADR を書く。これまで ADR に書いていた「決めてほしいこと」は、企画 Issue に書き、ADR には「所有者の判断」として結果だけを残す。
   - PR は `refs BL-NNN` と `refs #N`（企画）を書く。観察を完全に解消した PR は `closes #M`。

3. **閉じ方。** 観察は、直した PR がマージされたとき、または企画に取り込まれたとき（企画へのリンクをコメントして閉じる）。企画は、スライスがすべて Done になったとき、または却下されたとき（理由をコメントして閉じる）。

4. **Issue を作らない場合。** 今のスライスの中で直せる問題（Issue にせず直す）。根拠のない思いつき（backlog の Ideas に 1 行）。スライスごとの Issue（backlog の行で足りる）。

5. **判断待ちの一覧は `label:needs-decision`。** 所有者はこれだけを見れば、何を決めれば開発が進むかが分かる。答えがそろったらエージェントがラベルを外す。

6. **手順は 1 か所に。** 使い方と判断の基準は `docs/dev/workflow.md` の「Issue の使い方」にだけ書く。`/propose` スキルはその手順を実行するだけで、基準を重複して持たない（`docs-sync` と同じ作り）。

## 検討した選択肢

- **Issue を使わず、会話と backlog だけで続ける:** 観察と検討が消え、判断待ちが見えない。今の状態。
- **スライスごとに Issue を作り、backlog を Issue で置き換える:** GitHub の標準的な形だが、並びと状態が Issue とファイルの 2 か所に分かれるか、`make docs-check` が検査している BL-ID を捨てることになる。ファイルの backlog は、エージェントが読み書きしやすく、PR の差分として見直せる利点がある。
- **GitHub Discussions で検討する:** 判断をチェックリストで追えず、PR からの参照も弱い。
- **ADR に「決めてほしいこと」を書き続ける:** 判断が ADR の文面に残るが、未決の一覧がなく、答えが会話に散る。

## 結果

- 観察と検討が残り、次のセッションが引き継げる。判断待ちが 1 つのラベルで一覧できる。
- 所有者は、会話の流れを追わなくても、Issue のコメントで判断を返せる。
- Issue の数が増えるので、庭仕事で滞留（`needs-decision` のまま 14 日以上）を報告することを後で検討する（backlog の Ideas）。
- 再検討の条件: 観察 Issue が放置されて増えるなら、作る基準を厳しくする。企画 Issue の「決めてほしいこと」が毎回空なら、企画はコメント不要の設計メモとして ADR に統合する。
