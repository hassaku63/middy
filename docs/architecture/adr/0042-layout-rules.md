# 0042. 配置の規則: 骨組みは media、部品は container、しきい値は表に 1 か所

- 日付: 2026-11-10
- 状態: Accepted

## 文脈

画面の幅（#353）と、今後の PWA の表示環境（ホーム画面からの全画面表示、安全領域）で、配置を変える場面が増える。分岐が増えると、次のことが起きやすい（#359）。

- しきい値の数字が CSS・E2E・文書に別々に書かれ、ずれる。#358 のときに、overview.md の古い記述を 1 か所見つけた。
- できることが、幅によって黙って欠ける。
- ある幅を直すと、別の幅が壊れる。

所有者は、価値があるなら取り入れてよいとした。ただし、仕組みのために場当たりのコードを増やさないこと、AI の読み合わせに頼る大まかなものでよいことを条件にした（#359）。

## 決定

- 規則を `docs/dev/conventions.md` の「配置」に書く。
  - 骨組みだけが画面を見る（media query）。部品は自分の箱を見る（container query）。
  - しきい値は内容から決める。
  - 分岐しなくて済む書き方を先に使う。
  - 幅でできることを変えない。
  - 端末を当てない。
- しきい値の値は、同じ節の表を正典にする。`experience.md` と `overview.md` は数字を書かず、表を参照する。
- 機械で守るのは、ESLint の設定でできることだけにする。`src` のコード（テストを除く）で、`navigator.userAgent` などの端末の当て推量と、`window.innerWidth` などの窓の大きさ、`screen` を禁止する（`no-restricted-properties`）。
- CSS の値が表にあるかの確認は、PR の自己点検（`/code-review`、`docs-sync`）で AI が読み合わせて行う。検査のスクリプトは書かない。

## 検討した選択肢

- A: 規則を書くだけ。軽いが、端末の当て推量のような明らかな違反も防げない。
- B: 規則と表を書き、CSS の値が表にあるかを確かめるスクリプトを `make check` に入れる。CSS を読むための独自のコードが増える。分岐が 3 つしかない今は、得られるものより保守の負担が大きい。
- C: stylelint などの道具を入れる。依存の追加になる（AGENTS.md）。
- D（採用）: 規則と表を書き、ESLint の設定を数行足し、値の確認は読み合わせで行う。

## 結果

- 端末や窓の大きさで分岐するコードは、lint で落ちる。
- しきい値を変えるときに直す文書は、表 1 か所になる。
- 表と CSS のずれは、読み合わせで見落としうる。見直す条件は、分岐が 10 を超えたとき、またはずれが 2 回見つかったとき。そうなったら B を検討する。
- 画面サイズの行列で不変条件を検査する E2E は、E2E を PR の CI で回すかの判断（#359）と合わせて決める。
