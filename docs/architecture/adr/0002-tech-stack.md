# 0002. Go バックエンド + React/TypeScript フロントエンドのモノレポ

- 日付: 2026-11-07
- 状態: Accepted

## 文脈

要件は「React フロントエンド、バックエンドは Go か Rust（仮置き、より適した手段があればそれでもよい）」。プロダクトの特性:

- 再生（Web Audio）、ピアノロール描画、チャット UI、PWA はブラウザ側の仕事。
- 音楽理論エンジンは決定論的なロジックで、テストで網羅したい。
- LLM API 呼び出しは API キーを守るためサーバー側。
- AI エージェントが自律的に開発を回すので、**ビルド・テストの速さ、規約の明確さ、依存の少なさ** が品質に直結する。

## 決定

- **バックエンドは Go 1.24**。標準 `net/http`（1.22+ のパターンルーティング）、`log/slog`、`encoding/json`。フレームワークなし。音楽理論エンジンも Go（`internal/music`）に置く。
- **フロントエンドは React 19 + TypeScript + Vite**。テストは Vitest + Testing Library、PWA は `vite-plugin-pwa`。状態管理・UI ライブラリは当面入れない。
- **モノレポ**（`backend/`, `frontend/`, `docs/`）。ルートの `Makefile` が唯一のゲート（`make check`）。
- フロント・バック間は **OpenAPI で契約**（ADR-0004）。

## 検討した選択肢

| 選択肢 | 利点 | 欠点 | 判断 |
| --- | --- | --- | --- |
| **Go**（採用） | コンパイル・テストが数秒、`gofmt`/`go vet`/テーブル駆動テストという強い慣例、依存が少ない、公式 Anthropic SDK あり | エンジンをブラウザで再利用しにくい（WASM は TinyGo 経由で制約あり） | AI の反復速度と秩序を最優先 |
| Rust | 型システムが強い、WASM でエンジンをブラウザ共有できる | コンパイルが遅く、借用チェッカとの格闘で AI の反復コストが上がる。Web API 周りのボイラープレートが多い | エンジンのブラウザ共有は現時点で必須要件ではない |
| TypeScript フルスタック（Hono/Node + 共有パッケージ） | 単一言語、エンジンをブラウザとサーバーで共有、型も共有 | 要件の「Go か Rust」から外れる。サーバー側の規律（lint・型だけ）が Go より緩く、依存が膨らみやすい | 有力だが、ユーザーの仮置きを尊重 |

## 結果

- 理論エンジンはサーバーにあるため、ユーザー操作への即時反映はサーバー往復（ローカルで数 ms〜数十 ms）になる。編集 UI は「Timeline JSON をローカルで操作し、分析だけサーバーに頼む」設計で吸収する。
- **再検討の条件**: (a) オフラインで生成・分析が必要になった、(b) 編集操作ごとの往復がユーザー体験上許容できない、のどちらかが M3 の検証で判明したら、エンジンの WASM 化（TinyGo）または TS への限定移植を ADR で検討する。
- 将来の依存候補（必要になったら ADR を書いて追加）: Go — `chi`（ルーティングが複雑化したら）, `anthropic-sdk-go`（BL-011 で追加予定）, `gomidi/midi`（SMF を自前で書かない場合）; TS — `tone`（Web Audio の抽象化が必要なら）, `zod`（API 境界の実行時検証）, `openapi-typescript`（型生成, BL-026）。
