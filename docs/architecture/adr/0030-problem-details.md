# 0030. エラー応答は RFC 9457 の problem detail にする

- 日付: 2026-11-09
- 状態: Accepted（所有者の判断は 2026-11-09 の会話。ADR-0004 の決定のうち、エラーの形の 1 行を置き換える。problem detail を使うのは `/api` の応答だけで、アプリのファイルと画面のエラーは ADR-0033 で平文にした）

## 文脈

ADR-0004 は、エラーを `{"error":{"code","message"}}` の独自の封筒にした。業界標準の索引（`.claude/skills/standards/index.md` の RFC 9457 の項目、BL-140）を作ったとき、HTTP API のエラーには標準の形（Problem Details for HTTP APIs、RFC 9457。RFC 7807 の後継）があり、middy の封筒はそれと違うことがはっきりした。

所有者は、仕様が変わることを承知のうえで、標準の形に移すと決めた。

制約:

- API の利用者は、同じ配備で配る middy のフロントだけ。ただし PWA は古い画面をキャッシュに持つので、新しい API に古い画面がつながることがある。
- nginx が自分で答えるエラー（404、405、413、503。ADR-0027）も、API と同じ形でなければならない。
- 画面の文言は、安定した識別子から選んでいる（`useIdeas.ts` の `code` による分岐）。

## 決定

1. **エラー応答は RFC 9457 の problem detail にする。** メディアタイプは `application/problem+json`。メンバーは次のとおり。
   - `type`: 問題の種類を表す絶対 URI。`docs/api/problems.md` の、その種類の見出しを指す（`https://github.com/hassaku63/middy/blob/main/docs/api/problems.md#invalid_request`）。RFC が勧めるとおり、開くと人が読める説明がある。
   - `title`: 種類ごとに決まった短い英語の要約。
   - `status`: HTTP のステータスコード。応答のステータスと同じ。
   - `detail`: この出来事に固有の、開発者向けの英語の説明（今の `message`）。画面には出さない。
   - `code`: 拡張メンバー。`type` の見出しと同じ snake_case の識別子（今の `code`）。画面の文言の選択に使う。RFC 9457 は拡張メンバーを認めている。
   - `instance` は使わない。
2. **問題の種類の一覧は `docs/api/problems.md` だけに書く。** 種類を足すときは、そこに見出しを足す。Go のテストが、Go の使う種類と文書の見出しの一致を確かめる。
3. **移行のあいだ、フロントは新しい形と古い封筒の両方を読む。** nginx が答える 4 種類は、BL-164 まで古い封筒のままだから。BL-164 で nginx も移したら、古い封筒を読む部分を消す。
4. **API の版（`/api/v1`）は変えない。** 利用者は同じ配備のフロントだけで、古い画面は、エラーの文言が汎用のもの（「〜できませんでした」）に変わるだけで動き続けるため。

## 検討した選択肢

- **A: RFC 9457 にし、`code` を拡張メンバーで残す（採用）。** 利点: 標準の道具や利用者がそのまま読める。画面の文言の選択は今のまま。欠点: `type` と `code` が同じことを 2 通りに言う。
- **B: RFC 9457 にし、`code` をやめて `type` で分岐する。** 欠点: フロントの分岐が長い URI になる。`type` の置き場所を変えると、画面の分岐も変わる。
- **C: `type` を `about:blank` にし、`code` だけで区別する。** 欠点: RFC は、`about:blank` のときは種類がステータスコード以上の意味を持たないとする。400 の `invalid_json` と `invalid_request` のように、同じステータスに複数の種類があるので合わない。
- **D: 今の封筒のまま。** 欠点: 標準の利用者や道具（API のクライアント、監視）が、エラーを機械的に読めない。

## 結果

- エラーの形が標準になり、`Content-Type` で problem detail だと分かる。
- `type` の URI は GitHub の `main` の文書を指すので、文書の置き場所を変えると URI も変わる。変えるときは、新しい ADR で移行を決める。
- nginx のエラー（BL-164）が移るまで、nginx が答える 4 種類だけは古い封筒のまま。フロントは両方を読む。
- 再検討の条件: API を middy の外の利用者に公開するとき（`type` を自分のドメインの URI にするか、`/api/v2` を切るか）。
