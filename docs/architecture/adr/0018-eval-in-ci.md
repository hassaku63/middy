# 0018. 実 API の評価を、PR のラベルで CI に走らせる

- 日付: 2026-11-08
- 状態: Accepted（所有者の判断は Issue #113）

## 文脈

実 API の評価（`make eval`）は、Anthropic の鍵を持つ所有者が手元で実行するしかなく、プロンプトや語彙を変えるたびに開発が止まっていた。所有者の希望は、開発の主役である AI セッションが、必要なときに自分の判断で評価を走らせ、その PR の中で直してからマージできること（#113）。

確かめた制約:

- このセッションは、鍵を見えないまま差し込む仕組み（クラウド環境のネットワーク秘密）を Anthropic の API には使えない。ワークフローの手動実行（`workflow_dispatch`）も、GitHub App に Actions の書き込み権限がないので使えない（403）。PR へのラベルの付け外しはできる。
- リポジトリは public で、Actions のログは誰でも読める。fork からの PR には、GitHub は `pull_request` で秘密を渡さない。
- `pull_request` で動くワークフローは、PR のブランチのワークフローとコードで動く。

## 決定

1. **PR に `eval` ラベルが付いたら、その PR のブランチで `make eval` をそのまま走らせる**（`.github/workflows/eval.yml`）。結果の表を PR にコメントし、成功でも失敗でもラベルを外す。同じ PR でラベルを付け直せば、何度でも測り直せる。
2. **いつ付けるかは AI が決める。** プロンプト・スキーマ・インテント・和音や型の語彙・評価のケースを変えた PR で、マージの前に付ける。基準と、悪化したときの扱いは `docs/dev/workflow.md` にある。関係するファイル（`scripts/ci-changes.sh` の `eval`）が何も変わっていなければ、鍵を使う前に止める。
3. **書き込み権限のある人のコードは信頼する。** ラベルを付けられるのは書き込み権限のある人（所有者と AI セッション）だけで、その人たちのブランチのコードが鍵と同じジョブで動く。今の書き手は所有者と AI だけなので、これを受け入れる。
4. **必須の守り（所有者の判断）:**
   - fork からの PR では、評価のジョブを起動しない（`head.repo` がこのリポジトリのときだけ）。`pull_request_target` は使わない。
   - 鍵は Environment `eval` に置き、評価を走らせる 1 ステップにだけ渡す。PR に書き込めるジョブ（コメントとラベル）は、PR のコードを動かさない。チェックアウトは資格情報を残さない。
   - 鍵は前払い制の料金体系なので、使いすぎは料金の仕組みで止まる。
5. **`eval.yml` を変える PR は、所有者が確認してからマージする。** `pull_request` は PR のブランチの `eval.yml` で動くので、鍵を渡すステップを広げる変更も、その PR の中で効いてしまう。AI はこのファイルの変更を自分でマージしない。

## 検討した選択肢

- **`main` へのマージで走らせる:** 鍵に触れるのはマージ済みのコードだけになるが、PR の不都合をマージ後に知ることになる。所有者の指摘で撤回した。
- **3 段に分け、鍵を持つ段では PR のコードを動かさない**（`workflow_run` で段のあいだをデータだけで渡す）: 鍵に触れるコードを小さく固定できる。ただし、その送信のコードも AI が書いてマージするので、所有者が一度読むことが信頼の起点になる。実装も大きい。今の書き手の規模では、手軽さと手元との一致が勝ると判断した。
- **PR へのコメント（`/eval`）で起動する:** public なので誰でもコメントでき、毎回書いた人の権限を確かめる必要がある。
- **手動実行（`workflow_dispatch`）:** GitHub App に Actions の書き込み権限を足す必要がある。

## 結果

- AI は、プロンプトや語彙を変えた PR で自分で評価を走らせ、その PR の中で直してからマージできる。所有者が手元で評価する必要はなくなる（手元の `make eval` も今までどおり使える）。
- 鍵が漏れうる経路は、書き込み権限のある人の push したコード（AI が誤って、または読んだ文書に誘導されて書いたものを含む）。漏れたら鍵を無効にする。
- 再検討の条件: 書き手が増えたとき、鍵を評価以外にも使うとき、または鍵の扱いに不安が出たとき。その場合は、3 段に分ける形に移る。
