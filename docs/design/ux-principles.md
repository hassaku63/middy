# UI/UX 設計の原則と手順

プロダクトに依らない共通の層。画面に何を残すかを決めるのはプロダクトの意思で、この文書はその意思の書き方、引き算を律する原則、新しい画面や操作を決めるまでの手順を定める。見た目（色、装飾、タイポグラフィ）は扱わない。

## 1. 層

| 層 | 問い | 変わる頻度 |
| --- | --- | --- |
| 意思 | 誰の何をどう変えたいか。何を優先し、何を捨てるか | ほぼ変わらない |
| 概念 | どんな概念があり、それぞれ何のためにあるか | ときどき |
| 流れ | 目的を果たすまでに、ユーザーがどの順で何をし、状態がどう変わるか | 機能ごと |
| 画面の約束 | 画面ごとの主目的、主操作、出すもの・出さないもの | よく変わる |
| 実装 | コンポーネント、状態、API | 頻繁に |

- 下の層の判断は、上の層を根拠にする。原則（3 章）はすべての層に効く制約で、何を残すかは決めない。
- 画面の要素は、どの流れの、どの概念の目的のためにあるかを上の層までたどれること。たどれない要素は削る候補にする。
- 上の 4 層の middy での中身は `docs/product/` に置く（意思は [intent.md](../product/intent.md)、概念・流れ・画面の約束は [experience.md](../product/experience.md)、価値の順位は [vision.md](../product/vision.md)）。

## 2. 意思の書き方

- **「X を Y より優先する」の形で書く。** Y も大事だが、衝突したら X を取る、という意味になる。何を捨てるかが見えるので、原則どうしの衝突を判定するのに使える。
- **理由は、ユーザーがどう変わるかで書く。** 作り手の好みでは書かない。
- **決めるのはプロダクトの持ち主。** エージェントは、既存の文書と持ち主の要望から推論した案を「仮」と明記して書き、それに沿って進めてよい。判断に迷う点は持ち主に返す。仮の意思は、持ち主が確定するまで仮として扱う。
- **変えるときは理由を残す**（ADR か、その文書を変える PR）。黙ってずらさない。

## 3. 原則

単純さとは、ユーザーが扱う概念が少ないことで、画面の要素が少ないことではない。複雑さは消えずに移るだけなので、ユーザーにしか決められないこと以外はシステムが引き受ける。学習を助ける画面では、内容そのものの難しさは削らず、操作や画面を理解するのに使う負荷を削る（認知負荷理論）。

根拠の詳細（何を言っているか、確からしさ、よくある誤用、一次情報）は、開発用の HCI の索引（スキル `hci`）にある。

| # | 原則 | 根拠 | 判断の問い |
| --- | --- | --- | --- |
| 1 | 1 画面に主目的は 1 つ、主操作も 1 つ | Nielsen「最小限の設計」、手がかり（シグニファイア）、Fitts の法則 | この画面の主操作は何か。ほかの操作はそれに従属しているか。主操作は形か大きさでほかと見分けられるか |
| 2 | 状態が生まれるまで出さない | 段階的開示 | 今の段階で、これはもう使えるか |
| 3 | 説明は対象の隣に、読める時間だけ出す | Mayer の空間的・時間的近接、一過性情報効果、WCAG 2.2.2 | 見比べるのに、視線や操作の往復が要るか。読み終える前に消えるなら、留まる場所か止める手段があるか |
| 4 | 選択肢を出す前に、既定値で決める | 既定値の力。初めての人は、違いを比べないと選べない | システムが決めて、後から変えられるようにできないか。選択肢を見せるなら、比べられる形か |
| 5 | モードではなく、対象への操作にする | Norman の概念モデル、モードエラー（Sellen ら） | ユーザーが「今どちらにいるか」を覚えておく必要があるか。モードが要るなら、状態が 2 か所以上に見え、取り違えても戻れるか |
| 6 | 画面より先に名詞（対象）を決める | オブジェクト指向 UX | この操作はどの対象に属するか |
| 7 | 正常なときは黙り、異常なときだけ知らせる | Nielsen「システム状態の可視化」 | 正常なときにも、これは必要か |
| 8 | 待ち時間を設計する | 同上 | 待つ間に何が見えているか。終わったら視線はどこへ行くか |
| 9 | 空の画面で始め方を見せる | Nielsen「記憶より認識」 | 初めての人が、何をすればいいかわかるか |
| 10 | 要素を足す側が必要性を示す | — | どの流れの、どの段階のためか言えるか |

## 4. 原則どうしの衝突

原則は互いに衝突する。どちらを取るかは原則からは決まらないので、2 章の意思で決め、その判断を画面の約束に書く。

- **2（出さない）と 9（認識）:** 隠すと静かになるが、隠したものは思い出してもらう必要がある。
- **4（既定値）と学習:** システムが決めるほど操作は楽になるが、自分で選ぶこと自体が学びになる場面がある（望ましい困難）。
- **1（主操作 1 つ）と流れの連続性:** 画面を分けると主操作は 1 つになるが、画面の往復が増える。
- **3（読める時間）と再生の速さ:** 音はシステムの速さで進み、文は読む人の速さで読まれる。再生に合わせて流すのは短いもの（名前、見出し）だけにし、長い文は留めるか、止めて読めるようにする。

## 5. 新しい画面・操作を決める手順

各段階は数行で書き、UI を変える PR に添える。

0. **目的:** どのシナリオの、どの価値仮説に効くか。どれにも当たらなければ止めて、backlog の Ideas に送る。
1. **概念:** 既存の概念への操作で済むか。新しい概念が要るなら、目的・状態・操作・動作原理（目的がどう果たされるかを示す短いシナリオ）を書く。
2. **流れ:** ユーザーの繰り返しのどの段階に入るか。手順と状態の変化。空、待機中、失敗のときにどう見えるか。
3. **画面の約束:** 主目的、主操作、「常に出す／必要なときだけ出す／出さない」。
4. **原則の点検:** 3 章の問いを通す。外れるなら理由を書く。衝突は意思で解く。
5. **確かめ方:** E2E と、6 章の指標。

画面の構成や主操作を変える判断（企画の Issue や ADR）では、3 の画面の約束を、確かめられる形の「契約」として `docs/product/experience.md` に書く（#286）。小さな UI の変更には求めない。契約に書くのは次の 4 つ。

- **主要なタスクと手順:** 誰が、何を達成するために、どの順で何をするか。前提と、達成したと分かる状態。
- **手順ごとの認知的ウォークスルー:** 6 章の 4 つの問いへの見込みの答え（何が手がかりで、何が前提か）。前提は「〜のはず」と書き、事実とは書かない。
- **配置の意図:** 何を最も目立たせ、何と何をまとめるか、その理由と原則（`hci` の索引の項目名）。
- **確かめ方の振り分け:** 決定的に確かめるもの（E2E と axe のテスト名）、原則から推定するもの（レビューで見る）、人で確かめるもの（所有者や利用者に試してもらう）。

## 6. 確かめ方

指標は目安で、目的にはしない。

- 最初の価値（middy なら最初の音）が届くまでの操作数と時間
- 初期画面で操作できる要素の数（アクセシビリティツリーで数える）
- 主操作にたどり着くまでの Tab の回数と、見出しの構造
- 自動で切り替わる文の、文字数と表示の秒数。読み上げ（`aria-live`）の対象になる文字数
- 変更ごとに流れをなぞる（認知的ウォークスルー）。主要なタスクの 1 歩ごとに、次の 4 つを問う。
  1. ユーザーは、この歩でするべきことを意図するか。
  2. そのための操作に気づくか。
  3. 操作と、したいことの対応が分かるか。
  4. 操作のあと、進んだことが分かるか。
- 節目に操作の録画を見直し、可能なら 5 人程度で課題を試してもらう。

### 指摘の書き方

レビュー（人でも AI でも）の指摘には、次を添える。原則に照らした指摘は、実際に使いにくいことの**仮説**であって、実測ではない。

| 欄 | 中身 |
| --- | --- |
| どこで | 画面の要素と、どのタスクのどの歩か |
| 種類 | 決定的（宣言した約束やテストに反する）／規則（WCAG のような検査できる規則に反する）／原則からの推定（`hci` の索引の項目名）／代理指標（操作数や秒数）／人による検証 |
| 重大度 | 高・中・低。起きる頻度、起きたときの影響、慣れても残るか、で決める |
| 確信度 | 高・中・低。推定なら、何を見て、何を前提にしたか |
| 改善案と確かめ方 | 直し方の案と、直ったことをどう確かめるか |

手元では `ui-review` スキル（`.claude/skills/ui-review`）が、画面を撮って文脈を共有しないサブエージェントにこの形で指摘させる。CI を落としてよいのは、決定的なものと規則のものだけ。原則からの推定は、PR のコメントや企画の Issue に書く。
