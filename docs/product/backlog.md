# バックログ

**AI エージェントはここから着手項目を選ぶ。** ルール:

- **Now** の中で上から順に、`Ready` の項目を 1 つ選ぶ。`Blocked` は依存が Done になるまで触らない。
- 1 項目 = 1 PR = 1 縦スライス。受け入れ条件をすべて満たして `Done` にする。
- Now にない機能は実装しない。思いついたら **Ideas に 1 行追記** して終わり。
- 項目を分割・追加・並べ替えるときは、この表を編集して PR に含める。並べ替えの理由も一言書く。
- サイズ: S = 半日以内 / M = 1 日 / L = 2〜3 日。L は着手前に分割を検討する。
- **Done 表は現在のマイルストーンと直前のマイルストーンの分だけ残す。** それより古い行はマイルストーン完了時に削除する（履歴は git にある）。削除した ID を参照している文書は `make docs-check` が検出するので、その文書を現状に合わせて書き直す。

ステータス: `Ready` / `In progress` / `Blocked(依存)` / `Done`

## Ideas（未評価。実装しない）

- ライトの地で、鳴っている瞬間の音符と打点の琥珀（#fbbf24）が地に対して 1.35:1 と薄い。琥珀は「今」の色（ADR-0055、ADR-0056）なので、選び直すなら 3 か所をそろえて（#402 の H）

- 分数コードの表記を、セカンダリードミナントと紛れない形に（`V/7` を `V⁶` か「V（3 度ベース）」と表示する。入力の書き方は変えない。#371 の M6）
- 固定できることを、押す前に見せる（和音そのものの手がかりか、枠に「この和音で止めて読む」。#279 の ui-review）
- 固定の印を、停止の ■ と紛れない形（ピンなど）に（#279 の ui-review）
- 再生中は解説の枠に見出しだけを出し、理由の文は固定か停止のときに読ませる（原則 3「読める時間だけ出す」。#279 の ui-review）
- 度数の地図を Chord Flow Chart に（T の延長の列と、和音どうしの「進みやすい」矢印。どの矢印を描くかは音楽理論の判断なので、domain-model と ADR で決めてから。#360）
- 三度圏の補助図（調の 7 和音を 3 度の輪に並べ、2 音を共有する隣が機能の仲間になることを見せる。「なぜ T の仲間か」の説明に。#360）
- キーの選択と転調のための五度圏（今のキーと近い調を円で見せる。#360）
- 緊張の曲線（Lerdahl の Tonal Pitch Space の、主和音からの距離をエンジンの純粋関数で計算し、タイムラインに沿って描く。#360）
- 転調（サビで半音上げるなど。1 つの例に調が 2 つになり、タイムライン・解説・キーの変更・度数の地図に影響する。#165 の F。別の企画にする）
- 1 つの例に対するバリエーション（代理コードへの置き換え、テンションでニュアンスを足す）
- メロディ生成（LLM ではなくルールベースから）
- Web MIDI 出力、外部音源
- api イメージの Go のビルドを、コミットごとに作り直さない（#266 の D）。ビルドのログ（#327 の image ジョブ）では、api イメージの約 1 分のうち `go build` が 39 秒。`go build` の層は、バックエンドが変わったときと、`VERSION`（コミットの SHA）が変わるたびに作り直され、CI では Go のビルドキャッシュ（cache mount）が引き継がれない。`ARG VERSION` を `go mod download` のあとへ動かしても縮むのは約 1 秒。縮めるなら、版を実行時に渡す（フロントエンドだけの変更で約 40 秒）か、ビルドキャッシュを CI に引き継ぐ（新しいアクションの依存になる）
- 共有リンク、サーバー側保存とアカウント
- 耳トレーニングモード（進行を聴いてローマ数字を当てる）
- 楽譜表示（VexFlow 等）
- 多言語 UI
- 月次の庭仕事で、`needs-decision` のまま 14 日以上の企画 Issue を報告する（ADR-0014）
- UI の予算を E2E で測る（初期画面の操作要素の数、最初の音までの操作数。`docs/design/ux-principles.md` の 6 章）
- 解説文を LLM に言い換えさせる（事実はエンジンの分析に限る。ADR-0003 の範囲内）
  - 狙い: 型を足すのにコードを変えずに済む。所有者が自分で型を書ける。作曲アプリや楽譜の標準形式の素材を取り込める。
  - 形式の候補: MIDI ファイル（SMF）、MusicXML、ABC 記法、または格子の記法（BL-122）を広げた独自の JSON / YAML。
  - 検討すること:
    - 今はコードとテストが守っている決まりを、読み込み時の検証に移せるか（拍子、声部、同時に要る手の数、どの型もいずれかのスタイルに属する、など）。
    - 型の意味（`chord` 声部はボイシングを、`bass` 声部はベースを弾く、スウィングや押しの効き方）を、その形式で書けるか。
    - 解説の文（`Description`）を誰がどこに書くか。
    - ファイルはバイナリに同梱するか、実行時に読むか。
    - 音符はエンジンが決定論的に作るという原則（ADR-0003）との関係。データは LLM の出力ではない。
  - 重い判断なので、企画（`/propose`）は Fable で行う（所有者の指定）。ゴールと作るものが見えたら、実装は Opus や Sonnet に任せる。
- ピアノロールの音名を調に合わせて綴る（今は常に # で、F major では和音の Bb と音の A#3 が食い違う。BL-079 の延長）
- 再生中に解説が和音ごとに読み上げられる量を、スクリーンリーダーで確かめて絞る（今は解説全体が `aria-live`）
